## File 6 — `apps/api/src/middleware/requireAuth.js`

```javascript
export function requireAuth(req, res, next) {
  const token = req.cookies.token;
  if (!token) return res.status(401).json({ error: 'Not logged in' });
  try {
    const decoded = jwt.verify(token, process.env.JWT_SECRET);
    req.userId   = decoded.user_id;
    req.tenantId = decoded.tenant_id;
    req.role     = decoded.role;
    next();
  } catch (err) {
    return res.status(401).json({ error: 'Session expired — please log in again' });
  }
}
```

**Uses `req.db`?** No — this middleware runs before `withTenant`.
Its job is to verify the token and stamp the request, not query the DB.

**Sets `tenant_id` manually?** No — it reads `tenant_id` from the
verified JWT and stamps it onto `req.tenantId`. It never writes to
the database.

**What breaks if removed?**
Every protected route becomes publicly accessible. Anyone can call
`/me`, `/dashboard`, or any future route without a valid token.

**Why `jwt.verify` inside try/catch?**
`jwt.verify` throws an error if the token is expired, tampered with,
or signed with a different secret. The catch block turns that thrown
error into a clean 401 response instead of a server crash.

**Why stamp `req.tenantId` here?**
So `withTenant` can read it in the next middleware. The two
middleware functions work as a chain — `requireAuth` extracts the
tenant identity, `withTenant` uses it to scope the database.

## File 7 — `apps/api/src/middleware/withTenant.js`

```javascript
export async function withTenant(req, res, next) {
  const client = await pool.connect();
  try {
    await client.query(
      "SELECT set_config('app.tenant_id', $1, true)",
      [req.tenantId],
    );
    req.db = client;
    await next();
  } finally {
    client.release();
  }
}
```

**Uses `req.db`?** This file CREATES `req.db` — it is the source.

**Sets `tenant_id` manually?** No — it passes `req.tenantId` (from
`requireAuth`) into `set_config`. It never hardcodes a tenant ID.

**What breaks if removed?**
Every handler falls back to `pool.query()` directly, which has no
tenant context. RLS is never activated. All tenants' data becomes
visible to all users. This is a complete data breach.

**Why `set_config` with `true` as the third argument?**
The third argument means the setting is LOCAL — it only applies for
the duration of this transaction or until the connection is released.
When `client.release()` runs in `finally`, PostgreSQL automatically
clears `app.tenant_id`. The next request that borrows this connection
starts clean with no tenant context.

**Why is `client.release()` in `finally` and not in `try`?**
`finally` runs whether the handler succeeded or crashed. If we put
`release()` only in `try`, a handler error would skip it and that
connection would never return to the pool. After enough requests the
pool runs out of connections and the server hangs permanently.

## File 8 — `apps/api/src/routes/auth/me.js`

```javascript
router.get('/me', requireAuth, withTenant, async (req, res) => {
  const userResult   = await req.db.query(
    'SELECT id, name, phone FROM users WHERE id = $1', [req.userId]
  );
  const tenantResult = await req.db.query(
    'SELECT id, name, slug FROM tenants WHERE id = $1', [req.tenantId]
  );
  return res.status(200).json({
    user:   userResult.rows[0],
    tenant: tenantResult.rows[0],
  });
});
```

**Uses `req.db`?** ✅ Yes — every query goes through `req.db`.

**Sets `tenant_id` manually?** No — never. `req.tenantId` comes
from the verified JWT via `requireAuth`. The handler never touches
tenant_id directly.

**What breaks if `pool.query` was used instead of `req.db`?**
RLS would not be active for those queries. The WHERE clause filtering
by tenant would be missing at the database level. A user could
potentially retrieve another tenant's data.

## File 9 — `apps/api/src/routes/auth/login.js` (updated)

**Uses `req.db`?** No — login runs before any session is established.
There is no tenant cookie yet to scope the connection to. Login uses
`pool.query` directly, which is correct here.

**Sets `tenant_id` manually?** No — it reads the tenant from the
Host header subdomain and verifies membership. It never writes
`tenant_id` into the database.

**Tenant isolation logic written by me (not AI):**
- Reading `req.headers.host`
- Splitting on `.` to extract the subdomain
- Querying `tenants WHERE slug = subdomain`
- Querying `memberships WHERE user_id = ? AND tenant_id = ?`
- Rejecting with 403 if user does not belong to that tenant
